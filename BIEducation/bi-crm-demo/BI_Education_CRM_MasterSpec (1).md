## 2. Модель данных (Entity Relationship)

```
Contact (Родитель) 1───* Child (Ребёнок)
Contact 1───* Deal
Child 0..1───* Deal            ← сделка ВСЕГДА привязана к конкретному ребёнку, не к родителю напрямую
Deal 1───* PaymentSchedule     ← график траншей, генерируется автоматически при выборе тарифа
Branch 1───* Deal              ← жёсткая привязка прайса к филиалу (не ручной ввод)
User(role, branch) ───ownership─── Deal
```

Ключевые поля `Deal`, которых пока может не быть в текущей схеме — сверить и добавить при необходимости:

- `pipeline_type`: `B2C_SCHOOL | B2C_KINDERGARTEN | B2B`
- `tariff_type`: FK/enum на прайс филиала (см. таблицу выше)
- `has_food`, `has_transport`, `has_second_child_discount` (bool)
- `entrance_fee_status`, `contract_status`, `first_tranche_status` (для точного трекинга под-шагов внутри стадии)
- `waitlist_position` (nullable int) — для очереди
- `is_duplicate_of` (FK на Contact, nullable) — для анти-дубль логики
- `source_city`, `source_branch_requested` — что зафиксировала форма при заходе лида (для гео-роутинга)

## 6. Движок тарифов и платежей (Tariff & Payment Engine)

Логика, которую агент должен закодировать как отдельный сервис/функцию, а не хардкодить в компоненте карточки:

1. При переходе в `TARIFF_SELECTION` (школы) или создании Deal (сады) — фронт запрашивает у бэка прайс-лист **по branch + grade + tariff_type** (никогда не вводится вручную).
2. Бэк возвращает: `base_amount`, `entrance_fee`, `installments[]` (даты + суммы по регламенту, см. таблицу раздела 1).
3. При сохранении Deal бэк **генерирует** записи `PaymentSchedule` (по одной на каждый транш + взнос + питание/развозка если включены), а не хранит один total_amount без разбивки.
4. Триггеры на каждую запись PaymentSchedule:
   - `D-3` — напоминание в WhatsApp/уведомление с кнопкой оплаты
   - `D-0` — проверка оплаты (в демо — просто кнопка "отметить оплаченным")
   - `D+2` — просрочка → задача менеджеру + пуш директору филиала
5. Скидка 10% на второго ребёнка — считается на уровне Contact (есть ли уже активный Deal с тем же parent_id и другим child_id в статусе WON/активен), применяется только к ALDI BI.

## 7. Четыре ключевых бизнес-риска → как проверить, что агент их реализовал

| Риск | Проверочный кейс для QA после реализации |
|---|---|
| Разрыв Родитель/Ребёнок | У одного Contact два Child, каждый со своей Deal и своим графиком платежей; итоговая сумма к оплате агрегируется на родителя |
| Сезонность/очереди | При отсутствии мест новая Deal автоматически получает stage=WAITLIST; при переводе занятой Deal в LOST — первая в очереди Deal получает уведомление |

## 8. RBAC: роли, права доступа и гео-роутинг

### 8.1. Роли (зафиксировано для демо — 3 роли)

| Роль (код) | Кто это | Область видимости |
|---|---|---|
| `HQ_ADMIN` | Управляющая компания BI Education | Все филиалы, полный CRUD, настройка тарифов, управление пользователями |
| `BRANCH_DIRECTOR` | Директор конкретного филиала | Только свой филиал, полный CRUD + финансы + ручные скидки/перенос дедлайна взноса |
| `SALES_MANAGER` | Менеджер по продажам филиала | Только свой филиал, создаёт/двигает сделки, не видит финансовый конфиг и чужие филиалы |

Расширение до 6 ролей (`HQ_ANALYST`, `FINANCE`, `CALL_CENTER`) в будущем — просто новые строки в этой же таблице, архитектура ролей не меняется.

### 8.2. Матрица прав

| Действие | HQ_ADMIN | BRANCH_DIRECTOR | SALES_MANAGER |
|---|---|---|---|
| Просмотр сделок | Все филиалы | Свой филиал | Свой филиал |
| Создание сделки | ✅ | ✅ (свой филиал) | ✅ (свой филиал) |
| Перемещение по стадиям / смена тарифа | ✅ | ✅ (свой филиал) | ✅ (свой филиал) |
| Удаление/архивация сделки | ✅ | ✅ (свой филиал) | ❌ |
| Просмотр графика платежей | ✅ | ✅ (свой филиал) | ✅ (свой филиал, read-only) |
| Отметить платёж оплаченным | ✅ | ✅ (свой филиал) | ❌ |
| Редактирование глобального прайс-листа/тарифов | ✅ | ❌ | ❌ |
| Управление пользователями | ✅ (все) | ✅ (только создание SALES_MANAGER своего филиала) | ❌ |
| Кросс-филиальная аналитика | ✅ | ❌ | ❌ |
| Ручная скидка/перенос дедлайна взноса | ✅ | ✅ (свой филиал) | ❌ (только запрос) |
| Merge дублей контактов между филиалами | ✅ | Видит кандидатов своего филиала, финальный merge между чужими филиалами — не может | Не видит |

### 8.3. Модель данных

```python
class Branch(models.Model):
    name = models.CharField(max_length=100, unique=True)
    city = models.CharField(max_length=50)

class User(AbstractUser):
    class Role(models.TextChoices):
        HQ_ADMIN = 'HQ_ADMIN', 'HQ Admin'
        BRANCH_DIRECTOR = 'BRANCH_DIRECTOR', 'Директор филиала'
        SALES_MANAGER = 'SALES_MANAGER', 'Менеджер продаж'

    role = models.CharField(max_length=30, choices=Role.choices)
    branch = models.ForeignKey(Branch, null=True, blank=True, on_delete=models.PROTECT)
    # branch = null допустим ТОЛЬКО для HQ_ADMIN — валидировать в clean()/serializer
```

### 8.4. Чеклист엔forcement на бэкенде (обязательно все 4 пункта)

1. Кастомный DRF `permission_class`, проверяющий `request.user.role` для действий типа "удалить", "редактировать прайс", "управление пользователями".
2. `ViewSet.get_queryset()` — обязательная фильтрация: `if user.role != HQ_ADMIN: qs = qs.filter(branch=user.branch)`.
3. `has_object_permission()` — повторная проверка `deal.branch == user.branch` при редактировании/удалении конкретного объекта (не полагаться только на queryset-фильтр).
4. Auth-ответ возвращает `role` + `branch` — фронтенд использует это ТОЛЬКО для скрытия UI-элементов, реальная защита всегда на бэкенде.

### 8.5. Гео-роутинг

- Входящая форма фиксирует `source_city` + `source_branch_requested` → Deal создаётся сразу с этим branch, переназначить на другой филиал может только `HQ_ADMIN`.
- Кросс-выбор (клиент интересуется двумя школами) → создаётся связанная дочерняя Deal + уведомление обоим менеджерам (cross-sell, не конкуренция).

## 11. Как правильно давать промпты AI-агенту (общее правило)

1. В каждом промпте указывать номер фазы и раздел этого файла — не пересказывать бизнес-логику своими словами заново, а ссылаться на файл.
2. Просить агента **сначала показать план изменений** (список файлов и что в них меняется), и только после подтверждения — писать код.
3. После каждой фазы — просить агента обновить сам этот MasterSpec (раздел 0 Gap Analysis), отмечая, что реализовано, чтобы не терять состояние между сессиями.
4. Не давать одному агенту сразу несколько фаз — контекст размывается, тарифы могут "поплыть" (например, агент может перепутать взнос Riviera 200k/350k с Quantum 200k).
